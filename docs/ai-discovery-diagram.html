Cisco AI Defense · DefenseClaw

AI Discovery, drawn from end to end

DefenseClaw answers one question before it enforces anything: what AI is installed or running on this machine? Four discovery surfaces feed one inventory — here is how each one moves data.

Source: cisco-ai-defense.github.io/defenseclaw/docs/ai-discovery

01 — Orientation

Where discovery sits in DefenseClaw

DefenseClaw is a governance layer around AI coding agents: a Go gateway on the data path, a Python operator CLI beside it, and connector hooks inside 14 agent runtimes. Every capability an agent reaches for is scanned, logged, and — depending on mode — blocked. AI Discovery is the scanner that inventories the machine rather than the traffic.

02 — The four surfaces

Four ways to ask the same question

Continuous

Gateway scanner

Fingerprints AI artifacts on a timer and emits ai_discovery events when something appears, changes, or disappears.

agent discovery enable
On demand

CLI discovery

Immediate connector inventory in one command. No gateway required, and it can run strictly local.

agent discover
Compliance

AIBOM

Provenance for skills, plugins, MCP servers, agents, models, and memory — hashed and version-stamped.

aibom scan --json
Admission

Registry

The approved catalog. Once required, anything discovered but unlisted is blocked until an operator approves it.

registry require --type skill
03 — Data flow

Three lanes over one machine

The same local surfaces feed three independent paths. They differ in who runs them, whether a gateway is involved, and what comes out the far end.

04 — Signal lifecycle

Why the event stream stays quiet

Every signal carries a state and two timestamps. Rescans move signals between states, but only the transitions leave the machine — a laptop with a stable toolchain produces almost no traffic after its first scan.

05 — Local models

Finding weights without loading them

Local model discovery is the part most likely to worry a privacy reviewer, so it is deliberately metadata-only and needs no running inference engine. Two scopes feed two readers, and neither reader ever touches a tensor.

07 — The 30-second tour

Run it now

One command walks the known connector paths — OpenClaw, Claude Code, Cursor, Windsurf, Gemini CLI, GitHub Copilot CLI and six more — checks config files and binaries, probes versions, and prints a table.

on-demand discovery · no gateway required
$ defenseclaw agent discover

# machine-readable
$ defenseclaw agent discover --json

# strictly local: nothing leaves the host
$ defenseclaw agent discover --no-emit-otel

# CI gate: fail if the gateway is unreachable
$ defenseclaw agent discover --require-otel

To cut noise on a shared or personal machine, narrow the scope rather than turning discovery off:

quieter continuous discovery
$ defenseclaw agent discovery enable --mode passive --scan-roots ~/work \
    --no-include-shell-history --no-include-network-domains
08 — Trust model

What discovery refuses to collect

  • Names, not valuesEnvironment variable names are recorded; their values never are. File paths are hashed, and redacted output keeps only basenames.
  • Headers, not weightsModel discovery reads bounded headers and small config metadata. It never reads tensor payloads and never calls an inference route.
  • Capped API readsLoopback listings stop at 1 MiB and 256 models, across five vetted local servers only.
  • Optional path trustSet require_trusted_binary_paths: true and version probes only execute binaries from safe directories.
  • Tamper-evident eventsContinuous-discovery events are HMAC-stamped per installation, so a modified event does not verify.
  • Separate switchesProvider-domain checks, shell history, package manifests, and env-name collection each toggle independently.
